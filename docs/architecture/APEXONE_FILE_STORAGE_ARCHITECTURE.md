# 2. Executive Summary

APEXONE يجب أن يتعامل مع الملفات الكبيرة من خلال فصل:

1. **File Metadata**
2. **Physical File Content**

قاعدة البيانات مسؤولة عن إدارة metadata وحالة الملف ومعلومات التحقق، بينما الملف الفعلي يتم تخزينه خارج Oracle Database.

التصميم الحالي يحتوي بالفعل على الجدول:

```sql
APP_FILE_METADATA
```

وهو مناسب جدًا ليكون طبقة metadata الأساسية.

لا توجد حاليًا حاجة لإضافة `BLOB` إلى هذا الجدول، ولا ينبغي إنشاء جدول `APEX_FILES` لتخزين المحتوى الثنائي للملفات الكبيرة داخل Oracle.

التصميم المستهدف:

```text
                    APEXONE APPLICATION
                           |
                           |
                    File Upload Request
                           |
                           v
                 +---------------------+
                 | File Storage Service|
                 +---------------------+
                     /             \
                    /               \
                   v                 v
        +------------------+   +------------------+
        | Oracle Database  |   | External Storage |
        |                  |   |                  |
        | APP_FILE_METADATA|   | Physical Files   |
        +------------------+   +------------------+
                 |                    |
                 |                    |
                 +--------+-----------+
                          |
                    Relative Path
                    Checksum
                    Size
                    Status
```

# 4. Current APP_FILE_METADATA Structure

الجدول الحالي يحتوي على 11 عمودًا:

| Column          | Type           | Nullable | Purpose                         |
| --------------- | -------------- | -------: | ------------------------------- |
| FILE_ID         | NUMBER         |       NO | Unique file identifier          |
| FILE_NAME       | VARCHAR2(255)  |       NO | Original/logical file name      |
| RELATIVE_PATH   | VARCHAR2(1000) |       NO | Relative storage path           |
| FILE_EXTENSION  | VARCHAR2(50)   |      YES | File extension                  |
| MIME_TYPE       | VARCHAR2(255)  |      YES | MIME content type               |
| FILE_SIZE_BYTES | NUMBER(19,0)   |      YES | Physical file size              |
| CHECKSUM_SHA256 | VARCHAR2(64)   |      YES | SHA-256 checksum                |
| FILE_STATUS     | VARCHAR2(30)   |       NO | Processing lifecycle state      |
| CREATED_AT      | TIMESTAMP      |       NO | Creation timestamp              |
| PROCESSED_AT    | TIMESTAMP      |      YES | Processing completion timestamp |
| ERROR_MESSAGE   | VARCHAR2(4000) |      YES | Processing error                |

# 5. Existing Identity Strategy

`FILE_ID` هو المفتاح الأساسي:

```sql
CONSTRAINT APP_FILE_METADATA_PK
PRIMARY KEY (FILE_ID)
```

والعمود يستخدم Oracle Identity:

```sql
FILE_ID NUMBER
GENERATED BY DEFAULT AS IDENTITY
```

وهذا يعني أن النظام لا يحتاج إلى توليد ID يدوي للملفات.

الـ primary-key index موجود في:

```text
APEXONE_INDEX
```

---

# 6. Existing File Location Strategy

الموقع المنطقي للملف يتم تمثيله بواسطة:

```text
RELATIVE_PATH
FILE_NAME
```

وهناك Unique Constraint:

```sql
CONSTRAINT APP_FILE_METADATA_PATH_UK
UNIQUE (RELATIVE_PATH, FILE_NAME)
```

وبالتالي لا يمكن للنظام تسجيل ملفين لهما نفس:

```text
RELATIVE_PATH + FILE_NAME
```

وهذا يوفر حماية مهمة ضد duplicate storage references.

```text
RECEIVED

```

```sql

```

---

## 7.2 File Size

حجم الملف يجب أن يكون:

```text
NULL
```

أو:

```text
>= 0
```

ويتم فرض ذلك بواسطة:

```sql
APP_FILE_METADATA_SIZE_CK
```

---

## 7.3 SHA-256 Checksum

إذا كان checksum موجودًا، فيجب أن يكون 64 hexadecimal characters.

الـ constraint الحالي:

```sql
APP_FILE_METADATA_CHECKSUM_CK
```

يستخدم:

```sql
REGEXP_LIKE(
    CHECKSUM_SHA256,
    '^[0-9A-Fa-f]{64}$'
)
```

وهذا مناسب لـ SHA-256.

# 10. Important Architectural Decision

## Do NOT store large file payloads inside APP_FILE_METADATA

لا نضيف:

```sql
BLOB
```

إلى:

```text
APP_FILE_METADATA
```

ولا نستخدم:

```text
CLOB
```

لتخزين binary file content.

السبب هو أن الغرض من الجدول هو metadata وليس physical storage.

---

# 11. What is APEX_FILES?

في المرحلة الحالية:

```text
APEX_FILES
```

**غير موجود في قاعدة البيانات.**

ولا ينبغي إضافته لمجرد وجود حاجة لتخزين الملفات.

إذا كان المقصود من `APEX_FILES` هو:

```text
جدول يحتوي BLOB لكل ملف
```

فهذا يتعارض مع architecture المطلوب لتخزين الملفات الكبيرة خارج قاعدة البيانات.

أما إذا كان المقصود:

```text
File Registry / Storage Abstraction
```

فيمكن دراسة إضافته لاحقًا، ولكن كـ metadata/control layer وليس كـ binary payload table.

# 12. Recommended External Storage Model

التصميم الموصى به:

```text
Oracle
|
+-- APP_FILE_METADATA
|
+-- File ID
+-- File Name
+-- Relative Path
+-- Extension
+-- MIME Type
+-- Size
+-- SHA-256
+-- Status
+-- Processing timestamps
|
v
External Storage
|
+-- Physical file
```

مثال:

```text
FILE_ID = 1025
FILE_NAME = invoice_2026_001.pdf
RELATIVE_PATH = documents/invoices/2026
```

يكون الملف فعليًا:

```text
<storage-root>/documents/invoices/2026/invoice_2026_001.pdf
```

بينما Oracle يحتفظ فقط بالـ metadata.

---

# 13. Storage Root

يجب ألا يتم تخزين absolute operating-system paths داخل:

```text
RELATIVE_PATH
```

لا نريد:

```text
C:\APEXONE\FILES\documents\invoice.pdf
```

ولا:

```text
<APEXONE_REPO>\storage\documents\invoice.pdf
```

بدلًا من ذلك:

```text
documents/invoices/2026/invoice.pdf
```

ويتم تحديد الـ root من configuration خارج الـ metadata.

مثال:

```text
STORAGE_ROOT
    |
    +-- C:\APEXONE\STORAGE
```

ثم:

```text
RELATIVE_PATH
    |
    +-- documents/invoices/2026
```

والـ application يقوم بتركيب المسار النهائي.

---

# 14. Why Relative Paths?

استخدام relative paths يسمح بتغيير مكان التخزين دون تعديل بيانات الملفات.

مثال:

### Environment A

```text
C:\APEXONE\STORAGE
```

### Environment B

```text
D:\APEXONE\STORAGE
```

### Production

```text
E:\DATA\APEXONE\FILES
```

في الحالات الثلاث يبقى:

```text
RELATIVE_PATH
```

كما هو.

وهذا يجعل database portable بين environments.

```text
                 +-----------+
                 | RECEIVED  |
                 +-----------+
                       |
                       v
                 +-----------+
                 | PROCESSING|
                 +-----------+
                    /     \
                   /       \

          +-----------+   +--------+

          +-----------+   +--------+
                |

          +-----------+

          +-----------+
```

# 17. RECEIVED

عند استقبال الملف:

```text
FILE_STATUS = RECEIVED
```

يجب أن يكون metadata record موجودًا.

مثال:

```text
FILE_NAME
RELATIVE_PATH
FILE_SIZE_BYTES
MIME_TYPE
CREATED_AT
```

وقد يكون checksum متاحًا في هذه المرحلة أو يتم حسابه أثناء processing.

---

# 18. PROCESSING

عندما يبدأ النظام معالجة الملف:

```text
FILE_STATUS = PROCESSING
```

هذه الحالة تمنع اعتبار الملف مكتمل المعالجة قبل انتهاء العملية.

---

# 19. PROCESSED

بعد نجاح المعالجة:

```text
FILE_STATUS = PROCESSED
```

ويتم تسجيل:

```text
PROCESSED_AT
```

ويجب أن يكون الملف الفعلي موجودًا ويمكن الوصول إليه.

---

# 20. FAILED

عند فشل المعالجة:

```text
FILE_STATUS = FAILED
```

ويتم تسجيل:

```text
ERROR_MESSAGE
```

ويجب عدم حذف metadata record لمجرد فشل processing.

الـ metadata نفسها تعتبر جزءًا من audit trail.

---

# 21. ARCHIVED

عند أرشفة الملف:

```text
FILE_STATUS = ARCHIVED
```

ويمكن أن يتم نقل physical file إلى:

```text
archive/
```

مع الحفاظ على المرجع المنطقي في database.

---

# 22. Checksum Strategy

الـ SHA-256 هو العنصر الأساسي للتحقق من integrity.

مثال:

```text
Physical File
     |
     v
SHA-256
     |
     v
CHECKSUM_SHA256
```

وعند القراءة أو النقل يمكن إعادة الحساب:

```text
stored checksum
       vs
calculated checksum
```

إذا اختلفا:

```text
INTEGRITY FAILURE
```

ويجب تسجيل الحالة المناسبة.

---

# 23. File Size Validation

يتم تسجيل:

```text
FILE_SIZE_BYTES
```

ويجب أن يطابق الحجم الفعلي للملف.

مثال:

```text
Database:
FILE_SIZE_BYTES = 5242880

Physical File:
5,242,880 bytes
```

إذا اختلف الحجم، فهذا مؤشر على مشكلة storage أو transfer.

---

# 24. Security Requirements

لا يجب السماح للمستخدم بإرسال:

```text
../
```

داخل `RELATIVE_PATH`.

ممنوع:

```text
../../secret.txt
```

أو:

```text
..\..\secret.txt
```

أو absolute paths.

يجب أن تقوم storage layer بعمل path normalization وvalidation قبل إنشاء physical path.

---

# 25. Path Traversal Protection

يجب رفض:

```text
../
```

و:

```text
..\ 
```

وabsolute paths.

كما يجب ألا يسمح المستخدم بتحديد:

```text
C:
D:
UNC paths
```

داخل relative path.

الـ application هو الذي يحدد root.

---

# 26. File Name Security

لا يجب الاعتماد على `FILE_NAME` القادم من المستخدم باعتباره physical file name بدون validation.

يجب التحقق من:

```text
length
characters
extension
path separators
reserved names
control characters
```

ويفضل في الملفات الحساسة استخدام internal generated storage name.

مثال:

```text
FILE_ID = 1025
```

والـ physical object:

```text
1025_8f3a...sha256
```

بينما:

```text
FILE_NAME
```

يبقى الاسم المنطقي الذي يظهر للمستخدم.

---

# 27. Logical Name vs Physical Name

من الأفضل الفصل بين:

```text
Logical File Name
```

و:

```text
Physical Storage Name
```

مثال:

```text
FILE_NAME:
invoice.pdf
```

لكن physical storage:

```text
objects/1025/8b/1025_invoice.pdf
```

هذا يمنع collisions ويجعل التخزين أكثر أمانًا.

---


# 35. Recommended Decision

القرار المعماري المقترح:

```text
DO NOT:
    Create BLOB table for large files

DO:
    Keep APP_FILE_METADATA

DO:
```

و:

```text
External File Operation
```

ليسا transaction واحدة بطبيعتها.

لذلك لا نفترض أن:

```text
INSERT metadata
+
write file
```

سيتم rollback معًا تلقائيًا.

لهذا السبب `FILE_STATUS` مهم جدًا.

---

# 44. Failure Scenario

مثال:

```text
1. Insert metadata
2. Start file upload
3. File write fails
```

النتيجة:

```text
FILE_STATUS = FAILED
ERROR_MESSAGE = ...
```

وليس ترك record غير معروف الحالة.

# 45. Successful Scenario

```text
1. Validate request
2. Create metadata
3. Write physical file
4. Calculate size
5. Calculate SHA-256
6. Verify file
7. Update metadata
8. Set PROCESSED
9. Set PROCESSED_AT
```

# 48. Implementation Rule

لا يتم إنشاء:

```text
APEX_FILES
```

حاليًا.

ولا يتم تعديل:

```text
APP_FILE_METADATA
```

إلا بعد تحديد storage provider/configuration contract.

الـ implementation التالي يجب أن يبدأ من:

```text
database/modules/core/
```

مع الحفاظ على:

```text
APEXONE_DATA
APEXONE_INDEX
```

والـ existing constraint/index architecture.

# 49. Final Recommendation

الـ architecture الحالية ليست ناقصة من ناحية metadata.

بالعكس، `APP_FILE_METADATA` الموجود بالفعل يوفر foundation جيد جدًا لـ external file storage.

الناقص هو **Storage Layer** وليس BLOB Table.

لذلك الترتيب الصحيح للتنفيذ هو:

# 50. Architectural Conclusion

**APEXONE يجب ألا يجعل Oracle مخزن الملفات الكبيرة.**

Oracle يحتفظ بالـ metadata والـ lifecycle والـ integrity information.

الملف الحقيقي يعيش في external storage.

وبذلك نحصل على:

```text
Smaller Database
Better Backup Separation
Scalable File Storage
Checksum Verification
Clear Lifecycle
Provider Independence
Better Enterprise Architecture
```

والأهم أن هذا التصميم **متوافق مع الهيكل الحالي للمشروع وقاعدة البيانات التي تم التحقق منها فعليًا**، بدل إدخال جدول جديد غير موجود أو تغيير مسؤولية `APP_FILE_METADATA`.

**Baseline معتمد للتنفيذ:**

```text
APP_FILE_METADATA
        ↓
Metadata Registry
        ↓
External File Storage
```

وليس:

```text
APP_FILE_METADATA
        ↓
BLOB
        ↓
Oracle Database
```
