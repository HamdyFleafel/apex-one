
# REST/ORDS Adapter Specification v1 — Create User

## 1. Purpose

This document defines the architecture specification for the future REST/ORDS adapter responsible for user creation in APEXONE.

The adapter exposes the external transport contract and translates the external request into the existing Identity service API:

`PKG_IDENTITY.CREATE_USER`

This specification defines the transport boundary only.

It does not implement an ORDS module, REST endpoint, database procedure, or APEX page.

---

## 2. Architectural Position

The REST/ORDS adapter is a transport adapter and must not become a second Identity business-service layer.

```text
HTTP Request
     |
     v
REST / ORDS Adapter
     |
     v
Integration Boundary
     |
     v
PKG_IDENTITY.CREATE_USER
     |
     +--> PKG_SECURITY_HASH
     |
     +--> APP_USERS
     |
     +--> APP_PASSWORD_HISTORY
     |
     +--> PKG_ERRORS
     |
     v
USER_ID
     |
     v
REST / ORDS Response
```

Business rules remain owned by the existing Identity service.

---

## 3. Endpoint Contract

The baseline endpoint is:

`POST /api/v1/users`

The endpoint represents creation of a new Identity user.

The endpoint must not expose database table names or internal package implementation details.

---

## 4. Request Contract

The request body is JSON.

```json
{
  "username": "john.doe",
  "email": "john.doe@example.com",
  "password": "SensitivePassword"
}
```

### Required Fields

| JSON Field | Type   | Required | Identity Parameter |
| ---------- | ------ | -------: | ------------------ |
| `username` | string |      Yes | `P_USERNAME`       |
| `email`    | string |      Yes | `P_EMAIL`          |
| `password` | string |      Yes | `P_PASSWORD`       |

The transport layer performs only integration-level validation required to safely process the request.

Identity business validation remains the responsibility of `PKG_IDENTITY`.

---

## 5. Request Mapping

The adapter maps the JSON request directly to the Integration Boundary contract.

```text
request.username  -> P_USERNAME
request.email     -> P_EMAIL
request.password  -> P_PASSWORD
```

The resulting service invocation is conceptually:

```text
PKG_IDENTITY.CREATE_USER(
    P_USERNAME => request.username,
    P_EMAIL    => request.email,
    P_PASSWORD => request.password
)
```

The adapter must not duplicate:

* username uniqueness validation;
* email uniqueness validation;
* password hashing;
* password-history management;
* user persistence;
* Identity error generation.

---

## 6. Success Response

When user creation succeeds, the adapter returns the newly created identifier.

Baseline response:

```json
{
  "user_id": 1001
}
```

### Success Status

`HTTP 201 Created`

The response must expose the external identifier only.

Internal persistence details must not be returned.

---

## 7. Error Transport Contract

The adapter preserves the semantics of errors generated by the Identity service while translating them into the transport representation.

The Identity layer currently uses:

* `PKG_ERRORS.RAISE_IDENTITY_ERROR`
* `PKG_ERRORS.RAISE_ERROR`

The adapter must not create a competing Identity error taxonomy.

### Baseline Error Response

```json
{
  "error": {
    "message": "Username already exists."
  }
}
```

The exact external error-code taxonomy is intentionally deferred until the centralized API error standard is formally established.

---

## 8. HTTP Status Mapping

The initial transport mapping is:

| Condition                                          |                 HTTP Status |
| -------------------------------------------------- | --------------------------: |
| User created successfully                          |               `201 Created` |
| Malformed JSON / invalid transport request         |           `400 Bad Request` |
| Missing required input                             |           `400 Bad Request` |
| Authentication failure                             |          `401 Unauthorized` |
| Authorization failure                              |             `403 Forbidden` |
| Identity conflict, such as existing username/email |              `409 Conflict` |
| Unexpected internal failure                        | `500 Internal Server Error` |

The final mapping of specific `PKG_ERRORS` codes to HTTP statuses is deferred until the centralized API error taxonomy is established.

---

## 9. Authentication Boundary

Authentication is part of the external transport boundary.

Authentication implementation is not defined by this v1 specification.

Therefore:

```text
Authentication
     |
     v
REST / ORDS Security Layer
     |
     v
Create User Adapter
```

The Identity service itself remains responsible for Identity business rules and must not be coupled to HTTP authentication mechanisms.

---

## 10. Authorization Boundary

Authorization is external to `PKG_IDENTITY.CREATE_USER`.

The future adapter may require a permission such as:

`USER_CREATE`

However, the exact permission and authentication mechanism are not introduced as part of this v1 transport implementation.

Authorization policy remains subject to the platform security architecture.

---

## 11. Password Security

The `password` field is sensitive.

The adapter must:

* never persist plaintext passwords;
* never log plaintext passwords;
* never include passwords in diagnostics;
* never return passwords in responses;
* never write passwords to audit records;
* pass the password only to the Identity service invocation.

Password hashing remains owned by:

`PKG_SECURITY_HASH`

Password-history persistence remains owned by:

`PKG_IDENTITY`

---

## 12. Persistence Boundary

The REST/ORDS adapter has no direct persistence responsibility.

It must not directly access:

* `APP_USERS`
* `APP_PASSWORD_HISTORY`

The persistence path remains:

```text
REST / ORDS Adapter
        |
        v
PKG_IDENTITY.CREATE_USER
        |
        +--> APP_USERS
        |
        +--> APP_PASSWORD_HISTORY
```

---

## 13. Transaction Boundary

This specification does not assign commit or rollback ownership to the REST/ORDS adapter.

The adapter must not introduce an implicit transaction contract that conflicts with the existing database service architecture.

Transaction behavior remains subject to the implementation layer invoking `PKG_IDENTITY.CREATE_USER`.

---

## 14. External Response Boundary

The external API must not expose:

* Oracle table names;
* sequence names;
* internal package implementation;
* password hash;
* password salt;
* internal database errors;
* internal SQL statements.

The transport response represents the public API contract, not the internal database implementation.

---

## 15. Architectural Rules

The REST/ORDS adapter must follow these rules:

1. Transport logic belongs to the adapter.
2. Integration mapping belongs to the integration boundary.
3. Identity business rules belong to `PKG_IDENTITY`.
4. Password hashing belongs to `PKG_SECURITY_HASH`.
5. Identity error generation belongs to `PKG_ERRORS`.
6. Persistence remains behind the Identity service.
7. The adapter must not duplicate Identity business logic.
8. The adapter must not access Identity tables directly.
9. The adapter must not log sensitive password values.
10. HTTP concerns must not leak into the Identity service API.

---

## 16. Non-Goals

This specification does not define:

* actual ORDS module creation;
* actual REST endpoint deployment;
* database REST enablement;
* authentication implementation;
* authorization implementation;
* centralized API error taxonomy;
* OpenAPI generation;
* APEX page implementation;
* session management;
* role assignment;
* audit orchestration;
* centralized logging implementation.

---

## 17. Version and Status

* **Version:** v1
* **Status:** Architecture Baseline
* **Scope:** Create User REST/ORDS Adapter
* **Phase:** Phase 10
* **Implementation:** Deferred
* **Business Logic Owner:** `PKG_IDENTITY`
* **Transport Owner:** Future REST/ORDS Adapter

---

## 18. Acceptance Criteria

The specification is considered complete when:

1. The endpoint is defined as `POST /api/v1/users`.
2. The request contains `username`, `email`, and `password`.
3. Request fields map to `P_USERNAME`, `P_EMAIL`, and `P_PASSWORD`.
4. Successful creation returns `user_id`.
5. Successful creation uses HTTP `201 Created`.
6. Identity business validation remains inside `PKG_IDENTITY`.
7. The adapter does not directly access Identity persistence tables.
8. Plaintext passwords are never logged or persisted by the adapter.
9. The adapter does not expose internal database implementation details.
10. HTTP concerns remain outside the Identity service.
11. Authentication and authorization remain external transport concerns.
12. Transaction ownership remains explicitly undefined.
13. No ORDS implementation is introduced by this specification.
14. No competing Identity business-service layer is introduced.
